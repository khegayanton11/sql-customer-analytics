# Анализ клиентской базы и транзакций (SQL)

Анализ поведения клиентов розничной сети за 12 месяцев: 01.06.2015 — 01.06.2016.

**Задача:** понять, кто формирует выручку, как она распределена во времени и какие сегменты клиентов приоритетны для маркетинга.

**Стек:** MySQL 8.0 — CTE, оконные функции (`SUM() OVER`, `LAG()`), агрегация, `LEFT JOIN`, `CASE WHEN`, проверки качества данных.

---

## Ключевые выводы

> Замените `__` на значения из ваших выгрузок. Каждый вывод — цифра плюс что она означает.

- Непрерывную активность (покупки в каждом из 12 месяцев) показали **__ клиентов** — это **__%** базы. На них приходится **__%** выручки.
- Средний чек за период — **__**. Разброс по месяцам: от **__** (__) до **__** (__).
- Самый сильный месяц — **__** (**__%** годовой выручки), самый слабый — **__** (**__%**). Разрыв в **__ раза** указывает на выраженную сезонность.
- Возрастная группа **__** даёт наибольшую долю выручки — **__%** при доле в операциях **__%**, то есть покупает реже, но крупнее (средний чек **__** против **__** в среднем по базе).
- У **__%** клиентов не заполнен возраст и у **__%** — пол. Это ограничивает точность сегментации: группа `NA` формирует **__%** выручки.

**Что с этим делать:** __ (одна-две строки: какое действие бизнесу стоит предпринять по итогам анализа).

## Модель данных

```
customers                    transactions
---------                    ------------
Id_client  (PK)  ◄──────┐    id             (PK)
Gender                  └──  ID_client      (FK)
Age                          Id_check
                             date_new
                             Count_products
                             Sum_payment
```

Одна строка `transactions` — это **позиция в чеке**, а не чек. Поэтому количество операций везде считается как `COUNT(DISTINCT Id_check)`, а средний чек — в два шага: сначала сумма по каждому чеку, затем среднее по чекам. Прямой `AVG(Sum_payment)` дал бы среднее по позиции и занизил результат примерно вдвое.

## Содержание анализа

### 0. Проверки качества данных

Выполняются до расчётов, потому что дубликат ключа в справочнике при `LEFT JOIN` размножает строки транзакций и завышает все суммы.

- дубликаты `Id_client` в `customers`;
- коэффициент размножения строк (`COUNT(*) / COUNT(DISTINCT Id_client)`);
- транзакции с ключом, которого нет в справочнике (попадают в группу `NA`);
- границы дат и объём выборки.

**Результат проверок:** дубликатов __, осиротевших транзакций __ (__% от общего числа).

### 1. Клиентская активность
Клиенты с непрерывной активностью за 12 месяцев; операции, сумма и средний чек по каждому клиенту; средний чек за период; средняя сумма покупок клиента за месяц.

### 2. Помесячная динамика
Витрина по месяцам: выручка, чеки, клиенты, средний чек, доля месяца в годовых показателях. Отдельно — средние помесячные значения за период и прирост месяц к месяцу через `LAG()`.

### 3. Сегментация по полу
Доли M / F / NA по клиентам и по затратам внутри каждого месяца.

### 4. Сегментация по возрасту
Группы с шагом 10 лет и отдельная группа `NA`: сумма, количество операций, средний чек и доли — за весь период и поквартально.

## Технические решения

- **Фильтр по дате** задан как `date_new >= '2015-06-01' AND date_new < '2016-06-01'`. Полуоткрытый интервал вместо `BETWEEN` исключает двойной учёт граничного дня. Функции к столбцу в `WHERE` не применяются — индекс по `date_new` остаётся рабочим.
- **Доли** считаются оконными функциями (`SUM(x) OVER ()`, `SUM(x) OVER (PARTITION BY month)`) — это позволяет получить и абсолютное значение, и его долю за один проход, без самоджойна.
- **CTE вместо вложенных подзапросов** — запросы читаются сверху вниз, промежуточные наборы именованы.
- **`COALESCE(Gender, 'NA')`** — клиенты без данных не теряются при агрегации, а формируют отдельную группу.
